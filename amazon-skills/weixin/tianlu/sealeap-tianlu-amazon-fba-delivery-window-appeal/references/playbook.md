# Amazon FBA送达异常申诉 Playbook

## 适用问题

Use for FBA货件绩效异常申诉、送达窗口变更申诉材料准备、入仓时效问题追踪. Do not use to file a dispute without first confirming the shipment was actually affected by a platform-side interruption rather than the seller's own inbound delay.

## 输入证据

- marketplace、ASIN/SKU、库存阶段、补货与到仓时间
- 断货或备货前后的销量、流量、广告、自然位置和转化基线
- COGS、头程、仓储、平台费、退货和清仓成本
- 可比产品的成熟度、销量区间和需求趋势

## 决策路径

1. 核对当前账户后台对预计送达窗口的定义与本次货件被判定异常的具体口径，不沿用旧窗口天数的印象。
2. 用货件编号在通知邮箱与后台消息中检索配送中断或时间窗口调整类通知，完整保存原始通知内容，作为证据的时间戳来源。
3. 核对本次货件的绩效标记原因是否确系平台侧调整或中断所致，而非自身发货延迟、资料缺失等自身原因造成，避免对非平台责任的延误发起申诉。
4. 在货件问题详情页发起争议，用简洁英文说明原始窗口设置、附上平台通知证据，并明确指出延误的根本原因，避免主观归因或无证据陈述。
5. 提交后按后台展示的处理时效跟进结果；若被驳回，核对驳回理由是否指向证据不足或本次确非平台责任，再决定是否补充材料重新申诉。

## 经验假设与降级规则

- 送达窗口的具体天数、判定规则会随平台政策调整，来源提到的具体窗口天数仅供参考，执行前以账户当前后台展示为准。
- 申诉成功率与处理时效因证据完整度和本次绩效历史而异，来源关于多数卖家能成功撤销的说法是个案总结，不能作为申诉结果的保证。
- 仅当延误确系平台侧通知的中断或调整所致时才适用本流程；自身发货或资料问题导致的绩效记录应按对应问题分类处理，不应混用本申诉话术。

- 出现固定阈值、平台算法解释或因果结论时，改为待验证假设，并用当前站点与账户数据校准。
- 数据源冲突时保留各自口径，不取没有依据的平均数，也不选择更好看的结果。
- 第三方工具不可用、额度不足或 schema 改变时，记录缺口并停止；不得伪造调用结果。

## 输出检查

- 送达窗口口径与异常判定核对记录
- 配送中断/调整通知证据留存
- 申诉说明文本与提交记录
- 申诉结果跟踪与复核记录
- 每项建议都能回指当前任务中的证据或明确假设。
- 对未授权的线上变更保留草案；用户已有授权覆盖明确对象、动作与预算时可执行，并记录实际结果与回读证据。

## 指标口径补充

- 所有比率先统一站点、货币、对象、流量范围与归因窗口；分母为零或缺失时记为不可计算，不能解释为零成本或无限效率。
